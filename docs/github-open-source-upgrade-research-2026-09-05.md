> **研究对象**：屿航（Yūháng）本地优先、个人主页式网址导航站  
> **资料获取时间**：2026-09-05 21:56（UTC+8）  
> **结论标记**：**[事实]** 来自本仓库或公开项目资料；**[推断]** 是基于事实的分析；**[建议]** 是推荐行动。  
> **重要说明**：本轮 GitHub API、GitHub 页面与搜索服务均出现网络连接/额度限制，无法重新拉取实时 Star、提交频率、Issue 和 Release 数据。因此不把动态热度数字写成事实；候选项目链接和定位以仓库既有竞品报告中已记录的公开资料为基础，并明确列出时效局限。请在立项前由项目方复查各仓库的最新活跃度、许可证与安全公告。

## 0. 执行摘要

**[事实]** 屿航已不只是静态网址页：它具备公共目录、私有链接、收藏/工作区、模糊搜索、PWA/离线、导入导出、Supabase 同步、数据管理后台和 MV3 扩展 MVP；同时坚持“纯前端、零构建、双击即用”。来源：[README](../README.md)、[PRD](../prd.md)、[架构说明](../ROADMAP.md)。

**[推断]** 最大问题不是功能不足，而是“导航、起始页、工具、热搜、待办、排行、IP、媒体能力”共同竞争首屏注意力，削弱了“快速找到并保存链接”的主任务。第二个风险是本地—云端数据模型和 UMD 胶水层在持续扩展后会提高维护、同步与回归成本。

**[建议]** 未来 6 个月应按以下顺序投入，而非继续横向堆功能：

1. **P0：信息架构与链接实体收敛**——明确公共目录、个人链接、工作区入口、起始页快捷方式的边界。
2. **P0：把扩展做成可信的一键保存闭环**——当前扩展仅传递 URL 参数，尚未完成真正写入、去重、离线暂存和同步。
3. **P0：公共目录质量可见化**——官方标识、来源、最后核验、失效状态、替代链接与审核记录。
4. **P1：同步可靠性和可测试性**——版本、软删除、冲突提示、导入前备份，补足真实浏览器/移动端/无障碍测试。
5. **P2：验证后再扩展**——少量无敏感权限 Widget、备注/稍后阅读、模板分享；网页快照、复杂协作、重服务端能力暂缓。

这一路线保留屿航区别于 Docker Dashboard 和 SaaS 书签服务的核心优势：**低部署门槛、离线优先、中文目录治理与有情感识别度的个人数字入口**。

### 1.3 明显短板、约束与资料缺口

1. **定位与首屏负荷。** **[推断]** 核心价值是导航与保存，但热搜、工具、排行、待办、IP、媒体等横向能力会增加理解成本。应按“找链接 / 我的入口 / 辅助工具”分层，而不是让全部能力都争夺主导航位置。
2. **数据实体边界。** **[事实]** 已有 `links/sites` schema、链接规范化和多个存储空间，但目前 schema 为 V1，`merge()` 是按 id 覆盖合并，未体现删除墓碑、逐记录修改时间或冲突策略。来源：[schema.js](../web/js/schema.js#L8)。**[推断]** 跨端同步、扩展写入、投稿审核叠加后存在静默覆盖风险。
3. **架构扩展性。** **[事实]** 主站由多个全局 UMD 模块和 `app.js` 编排。来源：[架构说明](../ROADMAP.md#L11)。**[推断]** 该模式适合零构建，但新功能扩大时接口隐式耦合、回归范围和可观察性成本会上升。
4. **质量验证缺口。** **[事实]** 现有测试以 Node 逻辑和冒烟为主，维护文档明确“未覆盖像素视觉与动效流畅度”。来源：[架构说明](../ROADMAP.md#L91)。**[建议]** 补真实浏览器、移动视口、键盘、减少动态效果、PWA 离线和扩展端到端验证。
5. **目录事实冲突。** **[事实]** README 声明 `sites.tsv` 有 4214 条，架构说明仍称 1462 条。来源：[README](../README.md#L70)、[架构说明](../ROADMAP.md#L38)。**[建议]** 第一优先级修复文档与构建产物版本标记，避免产品、运营和数据治理对同一事实有不同认知。
6. **缺失的业务证据。** **[事实]** 仓库未提供 DAU、留存、搜索成功率、登录占比、同步失败率、扩展安装与保存成功率、移动占比、审核产能、商业目标。**[建议]** 把这些作为路线确认前的必答问题，而非以功能清单替代用户验证。

### 1.4 不可突破的升级约束

- **[事实]** 保持双击即用、零构建、离线优先，且核心重构不能破坏现有行为与测试门槛。来源：[架构说明](../ROADMAP.md#L61)。
- **[事实]** 网络集成必须显式开启、不得绕过 CORS/发送凭据/访问明显内网地址。来源：[网络集成边界](integrations.md#L51)。
- **[事实]** 媒体模块不做远程抓取、平台下载、DRM/鉴权绕过。来源：[媒体工具边界](media-tools.md#L5)。
- **[建议]** 任何引入服务器端目录审核、网页归档或团队协作的方案，都应以可选层方式存在，不应成为普通用户打开本地文件的前置条件。

## 3. 项目概况横向对比

| 维度 | 屿航 | Homepage / Dashy / Homarr | linkding / Linkwarden | Flame / Homer / Tabliss |
|---|---|---|---|---|
| 主定位 | 本地优先的个人数字入口 + 中文公共目录 | 服务器/家庭服务 Dashboard | 书签保存、知识沉淀，Linkwarden 可走向协作归档 | 起始页、应用/链接入口、可定制新标签页 |
| 核心用户任务 | 找站、保存、分类、跨设备恢复、快速打开 | 观察服务状态、聚合服务入口、定制面板 | 快速收藏、检索、组织、注释/归档 | 打开常用入口、个性化首页 |
| 部署模型 | 静态/PWA/单文件/双击即用，可选 Supabase | 多数依赖容器、服务端和第三方 API | 通常依赖数据库与服务端 | 静态配置或较轻的自托管 |
| 内容组织 | 公共目录、标签、收藏、个人站点、工作区、快捷链接 | 分组、页面、Widget、服务集成 | 标签、集合、备注、保存内容/归档 | 分组、链接/应用、页面组件 |
| 扩展模型 | MV3 MVP + 可选网络集成；尚未真正写入闭环 | 服务 API、Widget、图标与配置生态 | 扩展/API/导入导出，Linkwarden 更完整 | 模块/主题/配置为主 |
| 个性化 | 很强：主题、色彩、动效、起始页、IP | Dashy/Homarr 较强；Homepage 偏配置 | 功能优先，视觉克制 | 以主页样式和模块为主 |
| 离线与隐私 | 核心离线、网络显式 opt-in、RLS 同步 | 依服务端和部署环境 | 通常离不开后端与存储 | 静态模式较强，复杂能力有限 |
| 工程取舍 | 原生 UMD/无构建、测试脚本、数据管道 | 框架/容器/配置体系更强 | 后端模型、API、数据库迁移更成熟 | 简化配置和静态部署优先 |
| 对屿航的最大启示 | 保住轻量差异化 | 少量高价值组件和可视化编排 | 保存路径、实体模型、同步/审计边界 | 速度、可理解性、低门槛胜过大而全 |

**[推断]** 屿航不应与上述项目争夺同一个“全能自托管门户”位置。更优策略是：以公共目录品质和个人链接工作流为核心，吸收 Dashboard 的“局部组件化”、书签系统的“可靠保存与组织”、静态起始页的“即开即用”。

### 社区、文档、工程和增长机制的可学习点

- **[建议] 文档分层。** 借鉴成熟自托管项目的文档结构，至少拆为“普通用户快速开始、部署/离线说明、数据与隐私、扩展开发、维护者架构、贡献规范、变更日志”。屿航已有 README、PRD、架构说明与专项文档，是良好基础；下一步要消除数据数量冲突，并补 ADR（关键架构决策记录）。
- **[建议] 扩展成为增长入口而非孤立工具。** 参考 linkding/Linkwarden 的浏览器保存思路，扩展安装后首次保存成功率是重要北极星前置指标。当前屿航扩展安全边界良好，但仅是“跳转参数桥接”，需要完成确认写入与同步结果反馈。来源：[扩展 README](../extension/README.md#L22)。
- **[建议] 目录投稿闭环。** 将邮件投稿升级为“提交→URL 归一化→重复检测→分类建议→健康检测→人工审核→发布/驳回理由”，并给公共站点呈现来源和最近核验时间。它比排行榜/热搜更能形成可信内容资产。
- **[建议] 不以商业化功能反推产品。** 主题模板、工作区模板、托管同步或小团队空间可作为将来验证方向；在未验证留存与付费意愿前，不应引入广告、强推荐或复杂会员体系。

## 5. 本项目差距与机会

| 优先级 | 差距/机会 | 现状证据 | 推荐解法 | 预期结果 |
|---|---|---|---|---|
| P0 | 主任务不够聚焦 | 功能集合跨导航、工具、热搜、待办、排行、IP。 | 首页默认仅强调搜索/分类/收藏；把热搜、工具、排行、媒体收进二级入口；首次使用三步引导。 | 缩短首次点击时间，降低认知负担。 |
| P0 | 链接实体与权限边界不足 | schema V1 以 `links/sites` 为主；扩展未写入。 | 定义 `public_site`、`personal_link`、`workspace_item`、`shortcut`、`submission` 五类实体与可见范围。 | 避免私人链接污染目录，降低后续迁移成本。 |
| P0 | 扩展未形成保存闭环 | 扩展仅带 query 参数打开站点。 | 增加确认页、标签/备注、URL 规范化、重复提示、离线队列、可撤销写入与成功反馈。 | 建立高频获取入口与增长漏斗。 |
| P0 | 目录“可信度”不够可见 | 已有构建清洗和链接检查，但用户侧元数据有限。 | 增加 `official`、`source`、`lastCheckedAt`、`status`、`alternativeUrls`、审核日志。 | 公共目录从“数量”走向“可信、可维护”。 |
| P1 | 同步与删除冲突策略未显式化 | schema merge 按 id 覆盖；README 仅描述同步能力。 | 每条记录加 `updatedAt`、`deletedAt`、`revision`、设备/操作来源；冲突可预览，导入前备份。 | 降低跨端数据丢失与支持成本。 |
| P1 | 浏览器级质量保障不足 | 冒烟覆盖逻辑，未覆盖真实视觉/动效。 | Playwright 或等价浏览器测试；设备矩阵、离线、键盘、焦点、减少动态效果、扩展 e2e。 | 让“轻量却复杂”的体验可以稳定迭代。 |
| P1 | 社区贡献流程偏手工 | 有邮件反馈/提交收录，但缺结构化审核状态。 | 结构化投稿、审核队列、去重与健康自动检查、贡献指南、数据变更日志。 | 降低维护者人工成本，形成内容护城河。 |
| P2 | 个性化资产不能复用 | 有主题/设置/工作区，已有 schema 基础。 | 版本化导出“主题包/工作区模板”，默认模板库，后续只读分享。 | 增强留存和自然传播。 |
| P2 | 只打开 URL，缺少保存上下文 | 个人数据以链接、收藏、点击为主。 | 最小备注、稍后阅读、集合；仅在使用数据验证后试点 RSS/公开状态。 | 提高“保存后再利用”率。 |

## 7. 分阶段行动方案

### 短期：0–2 个月——让“找到并保存链接”成为明确主线

1. **信息架构重排**：设计并埋点验证“公共目录 / 我的链接 / 工作区 / 工具与发现”四层入口；默认首页强调搜索、分类、收藏。
2. **实体模型 V2**：在现有 `YHSchema` 基础上增加实体类型、来源、可见范围、更新时间、删除墓碑；编写 V1→V2 迁移、回滚和 diff 测试。
3. **扩展保存闭环**：从 query 参数桥接升级为明确确认后新增 `personal_link`；支持标签、备注、URL 规范化、重复处理、离线暂存与成功/失败状态。
4. **目录可信元数据**：后台与卡片增加官方标识、来源、最后核验、健康状态和候选替代链接；脚本产出带时间戳的健康报告。
5. **产品指标基线**：至少记录首屏到首次点击、搜索后点击率、搜索无结果率、收藏/保存成功率、扩展首次保存率、死链发现时间、同步冲突率（采集须透明、可关闭且最小化）。

**阶段验收**：新用户能在 30 秒内搜索或保存一条链接；个人链接不进入公共目录；历史数据可迁移且可恢复；目录卡片可说明可信度；核心流程离线不崩溃。

### 中期：2–6 个月——可靠同步与可维护生态

1. **同步可靠性**：记录级 revision、`updatedAt`、`deletedAt`、冲突预览与选择；导入/迁移前自动备份。
2. **质量工程**：引入真实浏览器测试，覆盖桌面/手机视口、PWA 离线、键盘导航、焦点可见性、减少动态效果、扩展保存主流程；保持 Node 测试快速执行。
3. **贡献与审核闭环**：结构化投稿、机器初检、人工审核、状态通知、发布日志；明确公共目录数据许可与来源规则。
4. **模板资产**：主题/工作区模板版本化导入导出、预览和恢复默认；先本地分享，再评估云端只读分享。
5. **有限内容能力**：先加私有备注、稍后阅读与集合，再以用户数据决定是否做 RSS/公共状态 Widget。

**阶段验收**：跨设备编辑不再静默覆盖；核心体验有浏览器级回归保护；维护者可以追溯一条公共目录变更；模板导入无破坏性。

### 长期：6–18 个月——形成可信的个人数字入口生态

1. **中文高质量公共资源目录**：官方认证、专题策展、地区/语言、替代链接、失效历史、维护记录。
2. **开放但受控的生态**：稳定 JSON schema、轻量 API、浏览器扩展、主题包、工作区模板；提供安全审查和版本兼容规则。
3. **可选服务化而非核心依赖**：在需求与成本被验证后，评估托管同步、小团队共享、可选内容存档；绝不破坏本地/静态入口。
4. **商业探索原则**：只在留存、贡献、同步和模板复用指标证明价值后，试验托管便利、团队治理或高级模板；避免广告驱动和强制推荐。

## 9. 不建议照搬的做法

1. **不要照搬 Homepage/Homarr 的 Docker、服务发现和大规模 Widget 体系。** 它们服务于家庭服务器/自托管服务面板；照搬会破坏屿航“文件即应用、离线核心可用”的产品承诺。来源：[Homepage](https://github.com/gethomepage/homepage)、[Homarr](https://github.com/homarr-labs/homarr)。
2. **不要近期做 Linkwarden/Hoarder 级网页抓取、快照、全文归档。** 这会引入服务端、存储、版权、隐私、恶意内容处理与高成本索引；先验证备注和稍后阅读。来源：[Linkwarden](https://github.com/linkwarden/linkwarden)、[Hoarder](https://github.com/hoarder-app/hoarder)。
3. **不要让热搜、排行榜和 Widget 取代导航主价值。** 这些可提高新鲜感，但会稀释用户“快速找到/保存”的任务，也会带来网络依赖。
4. **不要过早全量迁移 React/Vite 或重写所有模块。** 当前无构建和双击运行是硬约束；优先规范 schema、模块 API、事件边界和浏览器测试。只有在模块边界稳定、迭代速度被明确证实受限时，再局部引入构建链。
5. **不要仅按 Star 数、也不要把公开排行榜等同增长。** 应综合近期维护、许可证、贡献质量、文档、部署负担、隐私边界和与屿航约束的适配度。
6. **不要用广告、强推荐或隐性数据收集换增长。** 屿航的本地优先与可控性正是相对于第三方新标签页产品的信任优势。

## 11. 建议的立项复核清单

在选定任一外部项目作为实现参考前，逐项复核其：

- 仓库首页和 README 的定位、部署方式、许可证；
- 默认分支最近提交与近 90 天 Release；
- 安全公告、依赖与已知迁移；
- 文档是否覆盖升级/备份/隐私/扩展；
- 是否要求 Docker、数据库、第三方 Token 或服务器常驻；
- 与屿航“静态、离线、双击可用”约束是否冲突；
- 仅抽取产品模式和接口原则，避免复制受许可证保护的代码、品牌素材或数据。

**最终判断**：屿航下一阶段的胜负不在于做成更多功能，而在于把“可信公共目录 + 无摩擦私人保存 + 本地优先个人入口”做成可理解、可同步、可维护、可验证的一条主线。
